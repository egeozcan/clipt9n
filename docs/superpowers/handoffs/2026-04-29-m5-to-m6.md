Viewer events route through a second registered global hotkey, distinguished by `HotKey::id()` against the prompt hotkey in `drain_channels`.

## What's already there (M5 final state)

### History modules

- `src/history/crypto.rs` (~250 lines) — `derive_key(&Zeroizing<[u8;32]>) -> Result<Zeroizing<[u8;32]>, _>` (Argon2id with `Argon2::default()` params + a fixed `ARGON2_SALT: &[u8; 16] = b"clipt9n-history\0"`); `encrypt(key, plaintext) -> (Vec<u8>, [u8; 12])`; `decrypt(key, ciphertext, nonce) -> Zeroizing<Vec<u8>>`; `load_or_create_keyfile(path) -> Zeroizing<[u8; 32]>` (creates parent dirs; sets 0o600 on Unix via `crate::platform::set_owner_only_permissions`); `load_and_derive(path) -> Zeroizing<[u8; 32]>` (one-shot helper); `default_keyfile_path(config_dir) -> PathBuf`. The `cfg(unix)` / `cfg(not(unix))` switch in `set_keyfile_permissions` is the **single audited cross-platform-discipline exception in non-`platform/` code** — pure dispatch, the actual chmod lives in `platform/unix.rs`. Don't add more.

- `src/history/store.rs` (~480 lines) — `HistoryEntry { id, created_at, action, source_lang, target_lang, char_count, source: Option<Zeroizing<String>>, result: Option<Zeroizing<String>> }`; `NewEntry` (plaintext, owned-by-value so caller can drop); `QueryFilter { query: Option<String> }`; `History { conn: Mutex<Connection>, key: Zeroizing<[u8;32]> }` with `open(path, key)`, `in_memory(key)` (cleaner than feature-gating per M5 cross-cutting decision §11), `migrate` (idempotent CREATE IF NOT EXISTS), `count`, `insert`, `insert_with_cap` (prunes by `created_at` ASC after each insert), `query(filter, limit)` (per-row decrypt + Rust-side filter; failures log warn + skip), `delete(id)`, `clear_all` (rows wiped, key file untouched). Schema matches spec §7 verbatim including the `idx_created_at` DESC index. **`Connection` is `Send + !Sync` — wrap in `Mutex`, hold the lock briefly per call, never across an `await`.**

- `src/ui/history.rs` (~360 lines) — `HistoryModel { entries, query, selected, confirm_clear, show_corruption_banner }` derives `Debug + Clone` (required because `AppState` derives them); `HistoryOutcome::{ Close, CopyResult(i64), CopySource(i64), Delete(i64), ClearAll }`; pure helpers `ago_label`, `pair_label`, `pair_color`, `filter_entries`, `truncate_for_row`; `draw(ctx, &mut model) -> Option<HistoryOutcome>` paints the 680px design (search row, scrollable list, detail block, footer keymap, modal-on-top via `egui::Window`). View is paint-only; the App owns SQL queries, clipboard writes, and the `summon_history`/`refresh_history_model`/`update_showing_history`/`handle_keys_history`/`dismiss_history_to_idle`/`copy_to_clipboard` methods.

## Open considerations from M5's final review (M6 should know)

1. **Manual smoke from M5 plan §11.7 is still pending.** I (Claude) couldn't drive a real GUI session. The 13-step matrix at the end of `docs/superpowers/plans/2026-04-29-clipt9n-m5-encrypted-history.md` (lines 2899–3001) covers translate-then-restart-then-history, search/delete/clear-all, corruption simulation, wrong-key recovery, `store_text=false`, UTF-8. **Run this BEFORE merging M5 to main.** If any bug surfaces, file as Task 0 in the M6 plan.

2. **`Box<dyn Secrets>` is currently `_secrets` in `ClipApp::new`.** M6 revives it. Threading is unchanged from M3; just rename `_secrets` → `secrets` in M6's first wiring task and make `ClipApp` actually call it (currently it's dropped immediately).

3. **`Zeroizing<String>` discipline** is established (M1 for API key, M5 for decrypted history text). M6's setup wizard handles raw API keys at the input boundary — those should also live in `Zeroizing<String>` from text-edit field through to `keychain.set_password(...)`. Don't accidentally let a `String` leak through `format!()` or `to_string()` calls in the wizard's draw path.

4. **`Arc<Mutex<Connection>>` is the History sharing pattern.** rusqlite is `Send + !Sync`. Holding the lock across an `await` is forbidden (and won't compile under clippy with `#[deny(clippy::await_holding_lock)]` if added). M6's setup wizard doesn't touch History but if it ever needs to (e.g., to seed a sample row during the test-translation step), follow the same discipline: take the lock, run sync SQL, release, then await.

5. **Migration ergonomics: keyfile → keychain.** When the user upgrades from M5 to M6, the existing `<config_dir>/.history-key` should NOT be rotated. Read its bytes, copy into the keychain entry `history-key`, leave the file in place. Document this clearly in the README; users who care can `rm` the file after verifying. **Do not auto-delete** — silent destructive operations on user data violate the M3-era "best-effort" precedent.

6. **Connectivity-check retry policy** is spec-deferred (§13 open question; resolved as "one auto-retry, then surface"). M6 plan should encode this.

7. **History viewer dismiss restores prompt-default viewport size.** The shape is `match self.cfg.ui.density.as_str() { "compact" => 460.0, _ => 520.0 }` × 470.0. If M6 introduces a third viewport surface (setup wizard at, say, 580×640 per the design), the `dismiss_*_to_idle` helpers need to know which prompt size to restore. Consider a `prompt_default_inner_size(&self.cfg.ui)` helper to centralize the magic numbers.

8. **The `Modifier::Cmd` fallback in `main.rs`'s history-hotkey block is type-system happy-path only** — it's an unused value after the warn log because `mod_kind` is overwritten. If M6 unifies prompt + history hotkey registration into a `register_hotkey(cfg, manager) -> Option<u32>` helper, the fallback becomes naturally unreachable. Not a blocker; M5's review noted it as a refactor opportunity.

9. **HistoryModel derives `Debug + Clone`** because `AppState` derives them. The `Zeroizing<String>` inside `HistoryEntry` makes clone safe (zero-on-drop preserved per element). M6's setup wizard model — which holds the API key in flight — should similarly be in `Zeroizing<String>` and the model itself should derive `Clone` carefully (or not at all if AppState doesn't need it for setup; check whether `AppState::SetupWizard { model }` actually requires Clone).

10. **egui_kittest is unproven for clipt9n.** It's stable upstream and used by the egui project itself, but we haven't shipped a single test with it. Adopt incrementally: first one passing test, then expand. **Don't bet the M6 milestone on it.** Manual smoke remains the truth source for the full app integration; kittest is a regression net for the egui paint + keyboard layer specifically.

11. **M4 follow-ups still defer to M8.** Per the M4 review: Jinja conditional-branch validation gap, glossary entry validation, source-text lowercasing hoist, double-detection elimination, `[glossary] matching` value validation. Don't sneak them into M6.

12. **Plan structure.** Mirror M5's plan: ~10–12 tasks, each TDD-style with bite-sized steps and exact code. Self-review checklist at the end with spec-coverage table. Cross-cutting decisions glossary at the top. Reference the M5 plan path verbatim. Suggested split: M6.B tasks (egui_kittest setup + M5 backfill) come FIRST so M6.A's setup-wizard work uses the test infrastructure from day one.

13. **Cross-platform discipline.** `keyring` crate is already cross-platform; no `cfg(target_os)` needed in `secrets.rs`. The keychain-unavailable detection is also crate-handled. If M6 introduces any Windows-specific or Linux-specific code paths (it shouldn't), route them through `src/platform/`.

14. **Manual VoiceOver-like smoke matrix from M5 plan §11.7 step 11.7 is the model for M6's exit smoke.** Add a parallel manual matrix to the M6 plan covering: first-launch-no-key flow, invalid-key error path, sample-translation skip warning, keychain-unavailable fallback, restart-picks-up-keychain-key, accessibility-permission-revoked-on-macOS modal. Don't trust kittest alone; spec §7's setup wizard is the user's first impression of the app.
